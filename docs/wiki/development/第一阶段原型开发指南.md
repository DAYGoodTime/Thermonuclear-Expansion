## 范围与入口

本篇记录三台创造模式原型的实现，不代表生存配方、最终平衡或游戏验收。范围依据[第一阶段任务](../../../plan/2026-09-30-thermonuclear-stage1-tasks.md)及用户后续确认；产品规划与技术基线见[项目知识库](项目知识库.md)。下文 Java 路径均相对 `src/main/java/com/lin/thermonuclear/`。

`Thermonuclear.java` 转发生命周期：`CommonProxy.preInit()` 读配置并注册自有超超临界蒸汽，`init()` 注册 `GTFuelRodAdapter` 和三台机器，`loadComplete()` 解析自有与现有流体；流体缺失时对应路径拒绝运行。控制器引用为 `MachineLoader.nuclearPowerPlant`、`heatExchangeStation`、`largeSteamTurbine`，没有制造配方。

控制器通过 `registry/ModItems.register(ItemStack)` 调用 GTNHLib `AnimatedTooltipHandler.addItemTooltip`，按物品及准确元数据添加双语品牌标识；不改注册归属、NBT，不匹配其他 GT 机器元数据。NEI 提示词搜索使用 `#thermonuclear`，启用无前缀搜索后使用 `thermonuclear`；这不是模组归属搜索。

核电 I 与热交换四组仓室均有仅预览的直接放置回退：GT 仓室放置器要求 `WorldServer` 假玩家，而 NEI 的 `DummyWorld` 不满足。`@SideOnly(Side.CLIENT)` 的 `onPreviewConstruct()` 取得有效客户端玩家及 UUID；仅在预览标志、`constructing`、非 `WorldServer` 和目标为空气时将玩家传给 `ItemMachines.placeBlockAt()`，设置纹理与朝向。不能传 null 玩家：流体输入仓初始化默认模式前须建立拥有者 UUID，否则偏好表的空键会崩溃。回退的 `check()` / `spawnHint()` 恒为 false，不增加有效结构方块或候选、不覆盖已有方块、不绕过服务端放置；临时标志与玩家在 `construct()` 的 `finally` 清除，不写入 NBT。

`chainItemPipeCasings(-1, setter, getter)` 识别 `sBlockCasings11:0—7` 并提供同级约束及 `ITEM_PIPE_CASING` 建造通道。`clearHatches()` 将 `pipeTier` 重置为 -1，由结构重检推导，不信任 NBT 等级。批量上限为 `nuclearFuelRodsPerPipeTier×等级`，默认 256—2048 根；等级不改变单根寿命、效率或反射倍率。`getPipeTier()` / `getFuelRodLimit()` 对接 GUI 的 `pipe_tier` / `fuel_limit`。降级后超限批次完整保留并暂停燃料周期，待排乏燃料仍可输出。

仓室按 GT 接口与父类语义接入，兼容范围受机器和区域限制；核电拒绝双输入仓，热交换输入分区通过 GT 流体输入注册接入。涡轮要求流体输入、输出、有效发电仓及控制器内一件有效转子。重检显式清空扩展动力仓列表，避免 `.133` 父类造成重复计数。维护检查关闭、维修状态固定满值；涡轮磨损仍走父类组件检测与随机维护伤害路径，组件伤害参数为 `1`，不另写磨损公式。

## 燃料适配与核电模式

适配接口与注册表为 `api/FuelRodAdapter.java`、`api/FuelRodAdapters.java`；按注册顺序取第一个接受该堆栈的适配器。当前初始化仅注册 `nuclear/GTFuelRodAdapter.java`：接受 `ItemRadioactiveCellIC` 且子棒数为 1/2/4、能量与热量有限且为正、最大耐久为正、乏燃料非空的物品。耐久及产物通过该类 API 读取，不自动适配任意 `IReactorComponent`，也没有第三方覆写方法检测。

设 `c=numberOfCells`、`p=1+c/2+(stackSize>4 ? nuclearMaxReflectorCount : 0)`，其中 `c/2` 为整数除法：

- 单根发电基准：`sEnergy×c×p`；主机再乘 IC2 `balance/energy/generator/nuclear`、`nuclearDirectOutputMultiplier`、配置效率、实际寿命消费与批量。
- 单根理论热值：`c×round(p×(p+1)/2×sHeat)`，每个子棒分别取整；供热再乘 `nuclearHeatOutputMultiplier`、配置效率、实际寿命消费与批量。

反射规则依据工作堆栈数量，不要求实际反射板。燃料寿命按 20 tick 反应周期计，不按游戏 tick 直接扣减；没有温度加成。本模组热缓存不复刻 IC2 `reactorVent` / `selfVent` / `EmitHeatbuffer` 散热链，原版公式与实测边界见 [IC2 燃料棒公式](../references/IC2-2.2.828反应堆燃料棒公式.md)。

`FuelBatch.prepare(inputs, adapters, maxRods)` 先创建不修改库存的计划：最低剩余寿命优先，平局按遍历顺序；只合并物品、元数据及完整 NBT 相同的燃料，同一引用不重复装载，超额留在输入仓。检查成功后扣量，工作批次未耗尽时不混入下一批。乏燃料按出口容量分批排出，未排出部分完整保留并阻止新批装载；仅排产物的周期不推进启动。

| 模式 | 处理规则 |
| --- | --- |
| `DIRECT_GENERATION` | 不预热、不消费冷却液；每 20 tick 预付寿命，逐 tick 产电，末批按剩余寿命缩小 EU/t；要求有效发电仓 |
| `HEAT_SUPPLY` | 使用未来 20 tick 启动倍率平均值计算寿命消费，不产电；先计算已有缓存冷却，再检查计划产热；冷却后热量加本周期产热超过上限时直接关机，不缩减燃料消费来适配容量 |

效率由 `NuclearEfficiencyPolicy` 读取配置，不固定直发与供热的高低关系。模式切换由服务器检查关闭且未运行，不改变燃料、寿命、余量或待排产物；没有电路板物品或槽位。

- 热缓存默认上限为 50000，可由 `nuclearHeatCapacity` 调整并随 NBT 保存。开机且结构有效的供热模式每 20 tick 先冷却已有热量，再由燃料补充热量；冷却不要求有工作燃料，因此无新燃料、待排乏燃料或批次因降级超过装载上限时仍可排出余热。仅冷却或排乏燃料的周期不消费燃料，不推进预热，启动进度按停机规则衰减。开机直接发电模式不执行冷却。
- IC2 冷却液、超级冷却液和蒸馏水均按现有配置换算带走的热量；前两者输出对应热冷却液，蒸馏水输出普通蒸汽。`nuclear/NuclearCoolingMath.java` 将可冷却量限定为已有热量足够转换的整数升数，未满一升的热量保留在缓存，不向上取整，也不凭空输出热流体。
- 冷却批量同时受输入库存、热缓存、流体整数范围及出口容量限制。输出容量不足时通过独立事务模拟缩减批量，允许分批排热；所有正量输出均先预留，本周期检查通过后才扣冷却输入，ME 抽取确认后提交输出。连最小可输出批量都无法容纳时拒绝周期，不提交热量或余量变化。
- 计划产热按剩余燃料寿命和本周期平均启动倍率计算，不按热容量限流。冷却后热量加计划产热严格大于 `nuclearHeatCapacity` 时，通过 GT5U `.133` 的 `stopMachine(SimpleShutDownReason.ofCritical(...))` 关闭工作开关并保存超限原因；恰好等于上限允许。超限产热周期不消费燃料或冷却流体、不提交产物，内部热量及余量恢复周期前快照；必须手动重新开机，关机后由独立停机冷却周期排热。满负荷单周期产热本身超过容量时，即使供液和出口充足也会在启动过程中触发关机。
- 停机且热缓存非零时，不论当前模式，每 20 tick 尝试一次独立流体冷却；沿用 IC2 冷却液、超级冷却液、蒸馏水配方及出口限流，产生对应热流体或普通蒸汽。`ThermonuclearMultiblockBase.processIdleCycle()` 包住 GT 输入及输出事务，不启动生产进度、不消耗或装载燃料、不排乏燃料，也不改变工作开关及原停机诊断。有效结构、首次结构检查完成及邻近区块加载是停机冷却前提，暂停时不补算离线散热。
- 停机周期未能完成流体冷却（缺料、缺少仓室、出口堵塞、剩余热量不足以转换一升或输入事务失败）时，按 `nuclearPassiveCoolingPerSecond` 自然散热，默认 100 热量/秒，为用户选定的可配置原型值。每个 20 tick 周期最多减少 100 热量，热量最低为零；自然散热不消耗流体、不产生流体。流体冷却成功的周期不叠加自然散热。启动进度衰减和自然散热为独立机制。
- 蒸馏水按 `nuclearSteamPerDistilledWater` 产汽，不强制每批至少产出一升；不足一升的蒸汽作为专用小数余量跨周期、存档和控制器物品保存。正量蒸汽按出口容量限流，单批输出不超过 `FluidStack` 整数范围。余量不足一升时可以完成水耗与冷却而暂不输出蒸汽，后续批次累积足够后再输出；最终 GT 输入事务失败时热量、燃料和蒸汽余量恢复快照。

开机时首次可用冷却路径被选定后保持至关闭且停机；当前路径缺料时不会自动换成另一种。停机时每个冷却周期重新选择当前可用介质，优先 IC2 冷却液、超级冷却液、蒸馏水；不保证从单一物理仓室取液。核电冷却比例与热交换站 `hotPerWater` 分开配置。

## 热交换与蒸汽涡轮

`registry/WorkingFluids.java` 使用 `Materials.Steam`、GT 的 IC2 蒸馏水/冷却液访问器、`Materials.SuperCoolant` 和 `WerkstoffMaterialPool.HotSuperCoolant`。过热蒸汽和超临界蒸汽按当前 GT5U 注册约定解析 `ic2superheatedsteam`、`supercriticalsteam`。`registry/ModFluids.java` 在 preInit 注册自有[超超临界蒸汽](../fluids/超超临界蒸汽.md)，`WorkingFluids` 在 loadComplete 解析其引用；热交换站可生产该流体，尚无对应发电设备。任一被选择的蒸汽缺失时，该处理路径以 `fluids_missing` 拒绝运行。

`recipe/HeatExchangeRecipe.java` 提供两条独立路径：IC2 热冷却液、热超级冷却液各自配合蒸馏水，并完整返还对应冷却液。`HeatExchangeSteam.java` 定义普通、过热、超临界、超超临界四种输出，两条冷却液路径均支持全部四种蒸汽；GUI 仅在主机关闭且未运行时循环切换，服务端拒绝开机切换，选择写入 NBT。每周期仅处理一种热冷却液并输出一种蒸汽。

热交换站每 20 tick 尝试尽量处理当前选定热冷却液与蒸馏水，不再设置固定吞吐预算。先按两侧输入库存与 `hotPerWater` 计算完整转换批数，再用独立输出事务模拟二分查找 B/F 两侧剩余容量都能接受的最大批量；出口只能容纳部分时缩小批量，剩余输入留在仓室。水耗为整数升，热冷却液消耗为水耗乘 `hotPerWater`，冷却液等量返还。蒸汽产量为 `实际消耗热流体 L×所选倍率 + 该蒸汽的小数余量`，取整后输出；四种蒸汽余量独立保存，不足一升时允许暂不输出蒸汽。最终冷却液与正量蒸汽分别在 B/F 输出组模拟成功后才扣量，事务确认后当 tick 提交，再进入 20 tick 周期；连最小完整批量也放不下时零消费，无热源不产汽，单批输入输出受 `FluidStack` 整数上限约束。

旧配置 `exchangeHotFluidPerCycle`、`exchangeCycleTicks` 不再读取，也不再生成；现有配置文件保留这些键时不影响换热。旧 NBT `tnExchangeThroughputRemainder` 不再读取或写入，所选配方、原三种蒸汽类型及小数余量继续兼容。超超临界蒸汽追加至枚举末尾，使用 `ultrasupercritical` 标识；新增余量键 `tnExchangeSteamRemainder_ultrasupercritical`，旧存档缺失时为零。

涡轮使用 `MetaGeneratedTool01` 的 GT 转子元数据 170—179及 `TurbineStatCalculator`。实际蒸汽流体必须是 `Materials.Steam` 的实例，其他蒸汽等级或无关混入流体保持不变。转子流量属性仅作为有界容量，不作为最佳流量要求。流程为：

1. 转子蒸汽流量乘本模组容量倍率，限制实际吞吐。
2. 转子效率乘本模组效率倍率并封顶 1，保证普通蒸汽原始能量上限为 `0.5 EU/L`；不更改转子物品全局属性。
3. 转子和发电仓额定容量共同限制满负荷输出，低供汽仅按实际消耗量核算；启动倍率只降低电力。
4. 实际消耗蒸汽加冷凝余量，每 160 L 产生 1 L 蒸馏水，剩余 0—159 L 跨周期保存；水回收不受启动倍率影响。
5. 每 20 tick 扫描一次输入，蒸汽单批上限为每 tick 流量乘 20；EU/t 按实际批量除以 20，电力仍逐 tick 送出。即使本批尚不足一升，也预先核验一升水出口容量。没有蒸汽就不发电。

换转子检测包含实时物品对象、更换/移除槽位的 `onContentsChanged()` 和保存的转子指纹。指纹排除 `GT.ToolStats.Damage`，GT 自身磨损不清空启动进度；区块重载后使用已保存指纹匹配。损坏、移除或真正更换时清零。

## 启停、输出事务与存档

`StartupProgress` 为 0—1 的线性启动／衰减状态，不是温度或热缓存。供热与涡轮逐服务器 tick 推进，停机衰减，结构拆除清零；直发不预热。首次结构检查与邻近区块未加载时暂停处理，不因等待而衰减或清零；各机器检查范围见结构表。

公共层使用父类的正常周期推进、重检与组件磨损路径，`checkProcessing()` 统一设置 20 tick。发电返回 `GENERATING`，非发电成功返回 `SUCCESSFUL`；缺燃料、缺转子、物品／流体出口满使用 Registry 现有结果，专有错误使用已注册的 `SimpleCheckRecipeResult` 及双语 `GT5U.gui.text.recipe_result.*` 键。`onRunningTick()` 只送电与推进启动，不扫描物料，也不额外调用一次转子磨损。

输入使用 GT 事务引用，ME 物品按标识去重并保留遍历顺序，公共流体消费按引用去重；双输入接口通过 `getAllItems()` / `getAllFluids()` 接入，仍受结构区域限制。DEBUG 输入沿用上游虚拟供给语义；不重复调用 GTNL 注入父类的双输入事务。

输出先经 `FluidEjectionHelper` 模拟预留：公共出口使用同一 helper，热交换 B/F 分组各用一个。父类 `startRecipeProcessing()` / `endRecipeProcessing()` 包住消费，确认成功后提交全部回调；事务不跨 tick、不落盘，父类产物数组为空以防重复输出。ME 抽取失败时不提交产物或发电，核燃料恢复快照；上游可能已扣部分物料，不承诺跨网络完整回滚。结束后更新并标记输入仓室脏状态。

发电通过 GT 继承的 `addEnergyOutput(long)` 入口送出，该入口调用 `addEnergyOutputMultipleDynamos(long, true)`，统一处理普通与扩展动力仓；本模组不覆盖这两个函数、不直接调用 `increaseStoredEnergyUnits`。本项目 `.133` 的多动力仓函数在请求超过总额定容量时爆炸，内部注入计数使用 `int`，因此请求先取实际产电、有效动力仓额定总量与 `Integer.MAX_VALUE` 的最小值。这是旧 GT API 的安全限额，不是最终平衡数值。

GT 返回布尔值不等于实际送出 EU：逐仓调用前后储能正增量之和为 `sentEUt`，产电减送出为 `discardedEUt`；它们统计进入仓室的能量，不是外部电网接收量。分配与能量包行为交给 GT，不承诺满仓份额重分配。送不出的整 EU 作废，燃料／蒸汽仍消费；没有真实 EU 缓冲，仅保留亚 EU 取整余量，出口全堵或作废时连同余量丢弃。全堵时即使不足整数 EU 也告警，恰好填满且全送出不误报。

| NBT | 保存内容 |
| --- | --- |
| 公共状态 | 启动进度、亚 EU 余量、结构标记、带版本的 20 tick 周期进度、已付费周期 EU/t、启动推进标志与显示速率；无真实 EU 缓冲 |
| 核电状态 | 模式、数量为 1 的完整燃料／乏燃料代表堆栈、独立整数批次数量、寿命小数、蒸馏水产汽小数余量、所选路径及反应堆热缓存；世界存档另保存满负荷产热显示速率 |
| 涡轮状态 | 0—159 L 冷凝余量、排除磨损的转子指纹；转子与耐久由 GT 库存保存 |
| 热交换状态 | 当前热冷却液配方、所选蒸汽类型，以及四种蒸汽各自不足 1 L 的产出余量 |

`Count` 为有符号字节，燃料以数量 1 的完整代表堆栈加独立整数数量保存，读取范围 1—2048；旧存档缺少数量键时从堆栈恢复。非法数量拒绝，小数校验、进度限幅，缺省为零启动与直发模式；热缓存限于当前配置容量。仅版本匹配、有效的 20 tick 周期可在重载后续跑，产物不重复输出，旧一 tick 周期清空。关闭取消未送电力，不返还预付燃料／蒸汽；拆机物品携带核燃料状态及涡轮冷凝余量，不携带启动进度或周期电力。

核电产汽余量使用 `tnDistilledSteamRemainder`，合法范围为 `[0,1)`，旧存档缺失时为零。旧 `tnCoolantFraction_*` 与 `tnDistilledWaterFraction` 不再读取或写入：旧实现未将它们用于冷却计算，不能将其当作新的蒸汽余量迁移。未完成的整数升冷却转换保留的是 `tnReactorHeat` 中的热量。`tnFullLoadHeatRate` 仅用于世界存档恢复运行中显示，不随控制器物品携带。

### GUI info 字段与状态样式

三个具体 GUI 由各主机 `getGui()` 返回，`gui/ThermonuclearMultiblockGui.java` 提供终端布局与只读同步，保留启停、转子槽、结构诊断和停机原因。`displayKeys()` 为固定字段全集，`displayInfo()` 为可见字段映射；按 `tnLine_<字段名>` 注册无 setter 的 `StringSyncValue`，空字符串隐藏并由 `collapseDisabledChild()` 收起，切换模式无须重开。`formatInfo()` 统一翻译与格式，`getInfoData()` 使用同一映射。

| 主机／模式 | 当前显示 |
| --- | --- |
| 核电两模式共有 | 状态、模式、管道等级与批量上限（成型后）、燃料、热缓存与上限、产热速率；有工作燃料时显示数量、剩余周期及本批消耗 |
| 核电直发追加 | 启动显示 100%、满负荷与实际产电；不显示冷却路径 |
| 核电供热追加 | 启动进度、冷却路径及冷却液／热冷却液或水／蒸汽速率；不显示发电字段 |
| 核电待排产物 | 仅存在乏燃料待排出时追加该行，与核电模式无关 |
| 热交换站 | 状态、输出蒸汽、当前热流体配方、配方有效时的蒸汽倍率、热冷却液／蒸馏水实际消耗、蒸汽实际产出、冷却液返还；仅有处理周期时显示进度 |
| 蒸汽涡轮 | 状态、启动、满负荷与实际产电、转子耐久、蒸汽吞吐上限、普通蒸汽消耗、蒸馏水回收 |

终端不列发电仓额定、送出、作废数值或涡轮冷凝余量。流体速率以 L/t 显示，最多三位小数、去尾零、千位分隔；热交换水耗由当前热流体速率和 `hotPerWater()` 推导。状态颜色为运行绿、停机灰、等待黄、作废金、错误红，等级加粗；GT 事务失败细节仅在兜底失败状态显示，已知错误不重复叠加。标签灰、值青、模式金，中英文键一致。

核电的满负荷产热以热量/t 表示；满负荷热冷却液流量为产热速率乘所选冷却液的 L/热量比例，满负荷蒸馏水消耗为产热速率乘 `nuclearDistilledWaterPerHeat`。实际冷却液／水消耗和热流体／蒸汽输出分别取本批实际输入、输出升数除以 20；蒸汽输出包含小数余量的本批结算，不直接等同于水耗。满负荷流量是理论值，实际吞吐仍受热缓存、输入库存及出口容量限制。

Waila 通过服务端 NBT 显示核电／涡轮的产生和送出 EU/t，停机为零；热交换不显示发电信息。GUI 显示不替代物料、供热或送电结果验收。
