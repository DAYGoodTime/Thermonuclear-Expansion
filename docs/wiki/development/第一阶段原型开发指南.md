# 第一阶段原型开发指南

> 最后更新: 2026-10-09

## 范围与入口

本篇记录三台创造模式原型的实现，不代表生存配方、最终平衡或游戏验收。范围依据[第一阶段任务](../../../plan/2026-09-30-thermonuclear-stage1-tasks.md)及用户后续确认；产品规划与技术基线见[项目知识库](项目知识库.md)。下文 Java 路径均相对 `src/main/java/com/lin/thermonuclear/`。

`Thermonuclear.java` 转发生命周期：`CommonProxy.preInit()` 读配置并注册自有超超临界蒸汽，`init()` 注册 `GTFuelRodAdapter` 和三台机器，`loadComplete()` 解析自有与现有流体并调用 `HeatExchangeRecipes.register()`、`SteamTurbineRecipes.register()` 注册 NEI 展示；流体缺失时对应路径不可用。客户端 `nei/NEIThermonuclearConfig.java` 由 NEI 插件发现机制加载，添加独立超超临界蒸汽显示条目。控制器引用为 `MachineLoader.nuclearPowerPlant`、`heatExchangeStation`、`largeSteamTurbine`，没有制造配方。

控制器通过 `registry/ModItems.register(ItemStack)` 调用 GTNHLib `AnimatedTooltipHandler.addItemTooltip`，按物品及准确元数据添加双语品牌标识；不改注册归属、NBT，不匹配其他 GT 机器元数据。NEI 提示词搜索使用 `#thermonuclear`，启用无前缀搜索后使用 `thermonuclear`；这不是模组归属搜索。

核电 A 与热交换四组仓室均有仅预览的直接放置回退：GT 仓室放置器要求 `WorldServer` 假玩家，而 NEI 的 `DummyWorld` 不满足。`@SideOnly(Side.CLIENT)` 的 `onPreviewConstruct()` 取得有效客户端玩家及 UUID；仅在预览标志、`constructing`、非 `WorldServer` 和目标为空气时将玩家传给 `ItemMachines.placeBlockAt()`，设置纹理与朝向。不能传 null 玩家：流体输入仓初始化默认模式前须建立拥有者 UUID，否则偏好表的空键会崩溃。回退的 `check()` / `spawnHint()` 恒为 false，不增加有效结构方块或候选、不覆盖已有方块、不绕过服务端放置；临时标志与玩家在 `construct()` 的 `finally` 清除，不写入 NBT。

C 使用 StructureLib `ofChain` 接受 `sBlockCasings2:12—15`、`sBlockCasings8:1`、`sBlockCasings9:0`，可混用，默认提示及建造采用青铜管道外壳，不再使用 `fluid_pipe_casing` 分级通道。D 使用 `ofBlocksTiered` 同级约束与 `fuel_rod` 建造通道，默认一级；通道数量选择等级，超过最高级封顶。D 使用本项目四个注册方块，不接受钢框架；等级只由方块种类决定，允许元数据 0／4／8 混用朝向，默认提示、创造／NEI 建造保持元数据 0，不接受其他元数据。提示、创造建造、NEI 候选与检查来自同一元素。`clearHatches()` 和结构检查开始时将 `fuelRodTier` 重置为 -1，检查失败再次重置，由重检推导，不保存或信任 NBT 等级。四级热容量为 50000／100000／1000000／2147483647，最大并行为 8／32／128／512；无有效等级时容量与并行均为 0。

`getMaxParallelRecipes()` 接入 GT5U `.133` 电源面板的动态同步，返回至少 1 以维持合法输入范围；实际无有效等级时 `getFuelRodLimit()` 仍为 0。成型后手动并行范围为 1—当前等级最大并行；“始终使用最大并行”启用时锁定为上限，关闭后可手动输入。新批次装载上限为 `min(getMaxParallel(), getTrueParallel())`，不再读取管道容量配置。存档的 2048 根兼容上限保留；结构降级后超过等级最大并行的批次完整保留并暂停燃料周期，待排乏燃料仍可输出。仅降低面板设置不暂停已有批次，从下一批装载生效。GUI 在状态、模式之后显示 `fuel_rod_tier`、`max_parallel`、`fuel_limit`，另显示 `heat_capacity`，不改变单根寿命、效率或反射倍率。完整编译、实际面板交互及多人同步尚未验收。

参考 GTNL `common/machine/multiblock/AtomicEnergyExcitationPlant.java` 的分级组件元素与候选列表思路，核对本项目 GT5U `.133` 的 `Casings` / `ofAnyWater`、StructureLib `1.4.42` 的分级检查与建造行为，不复制参考代码、资源或数值。独立 Java 检查覆盖新结构全部 14616 格与导出草稿逐格一致（仅 E→G、H→~）、主机锚点和前墙法线、水平朝向／翻转的区块边界；完整模组编译、真实 NEI 显示、提示粒子与游戏内成型未验收。

## 燃料适配与核电模式

适配接口与注册表为 `api/FuelRodAdapter.java`、`api/FuelRodAdapters.java`；按注册顺序取第一个接受该堆栈的适配器。当前初始化仅注册 `nuclear/GTFuelRodAdapter.java`：接受 `ItemRadioactiveCellIC` 且子棒数为 1/2/4、能量与热量有限且为正、最大耐久为正、乏燃料非空的物品。耐久及产物通过该类 API 读取，不自动适配任意 `IReactorComponent`，也没有第三方覆写方法检测。

设 `c=numberOfCells`、`p=1+c/2+(stackSize>4 ? nuclearMaxReflectorCount : 0)`，其中 `c/2` 为整数除法：

- 单根发电基准：`sEnergy×c×p`；主机再乘 IC2 `balance/energy/generator/nuclear`、`nuclearDirectOutputMultiplier`、配置效率、实际寿命消费与批量。
- 单根理论热值：`c×round(p×(p+1)/2×sHeat)`，每个子棒分别取整；供热再乘 `nuclearHeatOutputMultiplier`、配置效率、实际寿命消费与批量。

反射规则依据工作堆栈数量，不要求实际反射板。燃料寿命按 20 tick 反应周期计，不按游戏 tick 直接扣减；没有温度加成。本模组热缓存不复刻 IC2 `reactorVent` / `selfVent` / `EmitHeatbuffer` 散热链，原版公式与实测边界见 [IC2 燃料棒公式](../references/IC2-2.2.828反应堆燃料棒公式.md)。

`FuelBatch.prepare(inputs, adapters, maxRods)` 先创建不修改库存的计划：最低剩余寿命优先，平局按遍历顺序；只合并物品、元数据及完整 NBT 相同的燃料，同一引用不重复装载，超额留在输入仓。检查成功后扣量，工作批次未耗尽时不混入下一批。乏燃料按出口容量分批排出，未排出部分完整保留并阻止新批装载；仅排产物的周期不推进启动。

| 模式 | 处理规则 |
| --- | --- |
| `DIRECT_GENERATION` | 不预热、不消费冷却液；每 20 tick 预付寿命，逐 tick 产电，末批按剩余寿命缩小 EU/t；要求有效发电仓 |
| `HEAT_SUPPLY` | 使用未来 20 tick 启动倍率平均值计算寿命消费，不产电；先计算已有缓存冷却，再检查计划产热；冷却后热量加本周期产热超过上限时直接关机，不缩减燃料消费来适配容量 |

效率由 `NuclearEfficiencyPolicy` 读取配置，不固定直发与供热的高低关系。模式切换由服务器检查关闭且未运行，不改变燃料、寿命、余量或待排产物；没有电路板物品或槽位。

- 热缓存上限由燃料棒方块等级决定：一级 50000、二级 100000、三级 1000000、四级 `Integer.MAX_VALUE`（2147483647）；旧 `nuclearHeatCapacity` 配置不再读取。缓存热量随 NBT 保存，降级不截断已有热量。开机且结构有效的供热模式每 20 tick 先冷却已有热量，再由燃料补充热量；冷却不要求有工作燃料，因此无新燃料、待排乏燃料或批次因降级超过装载上限时仍可排出余热。仅冷却或排乏燃料的周期不消费燃料，不推进预热，启动进度按停机规则衰减。开机直接发电模式不执行冷却。
- IC2 冷却液、超级冷却液和蒸馏水均按现有配置换算带走的热量；前两者输出对应热冷却液，蒸馏水输出普通蒸汽。`nuclear/NuclearCoolingMath.java` 将可冷却量限定为已有热量足够转换的整数升数，未满一升的热量保留在缓存，不向上取整，也不凭空输出热流体。
- 冷却批量同时受输入库存、热缓存、流体整数范围及出口容量限制。输出容量不足时通过独立事务模拟缩减批量，允许分批排热；所有正量输出均先预留，本周期检查通过后才扣冷却输入，ME 抽取确认后提交输出。连最小可输出批量都无法容纳时拒绝周期，不提交热量或余量变化。
- 计划产热按剩余燃料寿命和本周期平均启动倍率计算，不按热容量限流。冷却后热量加计划产热严格大于 `getHeatCapacity()` 时，通过 GT5U `.133` 的 `stopMachine(SimpleShutDownReason.ofCritical(...))` 关闭工作开关并保存超限原因；恰好等于上限允许。超限产热周期不消费燃料或冷却流体、不提交产物，内部热量及余量恢复周期前快照；必须手动重新开机，关机后由独立停机冷却周期排热。满负荷单周期产热本身超过容量时，即使供液和出口充足也会在启动过程中触发关机。
- 停机且热缓存非零时，不论当前模式，每 20 tick 尝试一次独立流体冷却；沿用 IC2 冷却液、超级冷却液、蒸馏水配方及出口限流，产生对应热流体或普通蒸汽。`ThermonuclearMultiblockBase.processIdleCycle()` 包住 GT 输入及输出事务，不启动生产进度、不消耗或装载燃料、不排乏燃料，也不改变工作开关及原停机诊断。有效结构、首次结构检查完成及邻近区块加载是停机冷却前提，暂停时不补算离线散热。
- 停机周期未能完成流体冷却（缺料、缺少仓室、出口堵塞、剩余热量不足以转换一升或输入事务失败）时，按 `nuclearPassiveCoolingPerSecond` 自然散热，默认 100 热量/秒，为用户选定的可配置原型值。每个 20 tick 周期最多减少 100 热量，热量最低为零；自然散热不消耗流体、不产生流体。流体冷却成功的周期不叠加自然散热。启动进度衰减和自然散热为独立机制。
- 蒸馏水按 `nuclearSteamPerDistilledWater` 产汽，不强制每批至少产出一升；不足一升的蒸汽作为专用小数余量跨周期、存档和控制器物品保存。正量蒸汽按出口容量限流，单批输出不超过 `FluidStack` 整数范围。余量不足一升时可以完成水耗与冷却而暂不输出蒸汽，后续批次累积足够后再输出；最终 GT 输入事务失败时热量、燃料和蒸汽余量恢复快照。

开机时首次可用冷却路径被选定后保持至关闭且停机；当前路径缺料时不会自动换成另一种。停机时每个冷却周期重新选择当前可用介质，优先 IC2 冷却液、超级冷却液、蒸馏水；不保证从单一物理仓室取液。核电冷却比例与热交换站的蒸汽换算分开处理。

## 热交换与蒸汽涡轮

`registry/WorkingFluids.java` 使用 `Materials.Steam`、GT 的 IC2 蒸馏水/冷却液访问器、`Materials.SuperCoolant` 和 `WerkstoffMaterialPool.HotSuperCoolant`。过热蒸汽和超临界蒸汽按当前 GT5U 注册约定解析 `ic2superheatedsteam`、`supercriticalsteam`。`registry/ModFluids.java` 在 preInit 注册自有[超超临界蒸汽](../fluids/超超临界蒸汽.md)，`WorkingFluids` 在 loadComplete 解析其引用；当前两种冷却液均禁止生产该流体，尚无其他生产路径，涡轮支持消耗它发电。热交换选定蒸汽缺失时以 `fluids_missing` 拒绝；涡轮跳过缺失燃料类型，蒸馏水流体缺失时拒绝运行。

`recipe/HeatExchangeRecipe.java` 提供两条独立路径：IC2 热冷却液仅产普通或过热蒸汽，热超级冷却液仅产超临界蒸汽；各自配合蒸馏水，并完整返还对应冷却液。`supportsSteam()` 同时约束实际处理和 NEI 注册，两种冷却液均拒绝超超临界。GUI 仅在主机关闭且未运行时循环切换普通、过热、超临界三种蒸汽，服务端拒绝开机切换，选择写入 NBT；每周期仅从支持所选蒸汽的热流体中选取一种，不会自动更改蒸汽类型。旧存档中不匹配所选蒸汽的冷却液不会被消费；没有匹配输入时报告缺少热流体。`HeatExchangeSteam.java` 保留超超临界枚举及存档标识，旧存档选中它时在库存检查、输出预留和消费前以 `steam_unsupported` 拒绝运行；停机切换可转回普通蒸汽。不消耗冷却液、蒸馏水或已付水耗额度。

热交换站每 20 tick 尝试尽量处理当前选定热冷却液与蒸馏水，不设置固定吞吐预算；最小批次为 **1 L 热冷却液**，不要求凑齐 160 L 蒸汽。IC2 热冷却液产普通、过热蒸汽分别固定为每 1 L 产出 40、20 L；热超级冷却液仅产超临界蒸汽，保留 5 倍系数，每 1 L 产出 50 L。三种受支持蒸汽均固定为每 1 L 蒸馏水提供 160 L 产汽额度，不因蒸汽类型或冷却液类型改变水汽比例；两种热冷却液均等量返还对应冷却液。IC2 热冷却液首次处理 1 L 产普通蒸汽时消耗 1 L 蒸馏水，返还 1 L 冷却液、输出 40 L 蒸汽并保留 120 L 水耗额度；热超级冷却液首次处理 1 L 时消耗 1 L 蒸馏水，输出 50 L 超临界蒸汽并保留 110 L 额度。额度跨批保留，用完后按实际产汽需要再次取水。

`recipe/HeatExchangeBatch.java` 按 `floor(热冷却液 L×所选配方的有效倍率 + 该蒸汽的小数余量)` 计算实际产汽量；不足 1 L 的蒸汽保留为各类型独立的小数余量。所需水量为 `ceil(max(0, 本批蒸汽 L−已有水耗额度)/160)`，新额度为 `旧额度 + 本批水耗 L×160−本批蒸汽 L`，始终处于 0—159 L。额度由两种冷却液、三种受支持蒸汽共用，停机、切换和存档不清零；没有热冷却液时额度不会自动产汽。GUI 的产汽倍率与批次处理共用配方有效倍率，包含热超级冷却液的 5 倍系数。

旧配置 `exchangeHotFluidPerCycle`、`exchangeCycleTicks` 不再读取，也不再生成；GTNHLib 加载配置时会清理这类未声明的旧键。旧 NBT `tnExchangeThroughputRemainder` 不再读取或写入，所选配方、原三种蒸汽类型及小数余量继续兼容。超超临界蒸汽追加至枚举末尾，使用 `ultrasupercritical` 标识；新增余量键 `tnExchangeSteamRemainder_ultrasupercritical`，旧存档缺失时为零。
先按热冷却液库存与整数上限确定候选热流体量，再用独立输出事务模拟二分查找蒸馏水和 B/F 两侧出口容量都能接受的最大整数升量；出口不足时可以缩至 1 L 热冷却液。冷却液及正量蒸汽模拟成功后才扣输入，事务确认后当 tick 提交输出、水耗额度及蒸汽余量，再进入 20 tick 周期；最小批次也放不下时零消费，额度和余量不变。已有额度足够支付本批产汽时允许无蒸馏水输入；额度不足且缺水则等待。单批输入、输出受 `FluidStack` 整数上限约束。

旧配置 `exchangeHotFluidPerCycle`、`exchangeCycleTicks`、`ic2HotCoolantLitresPerWater`、`hotSuperCoolantLitresPerWater` 及四种 `*SteamLitresPerHotCoolant` 倍率键不再读取或生成，已有键不能覆盖固定倍率或重新启用超超临界产出。旧 NBT `tnExchangeThroughputRemainder` 不再读取或写入；所选配方、蒸汽类型和 `tnExchangeSteamRemainder_*` 继续兼容，超超临界蒸汽继续使用 `ultrasupercritical` 标识，其旧小数余量仅保存而不参与产汽。新增 `tnExchangeWaterCredit` 保存已付水耗额度，缺失或越界时为零；世界存档和控制器物品均保留额度与蒸汽余量，实际水耗显示速率以 `tnExchangeWaterRate` 保存到世界存档。

涡轮无需 GT 转子，不读取转子效率、流量、耐久或指纹。`SteamTurbineFuel` 共用普通／过热／超临界／超超临界流体引用与 **1.5／4.5／7.5／10.5 EU/L** 基础能量，运行与 NEI 不分别维护数值。每周期仅选择一种库存为正的蒸汽，固定按上述顺序查找，不混烧；无关流体不消费。轴等级不限制蒸汽类型。耗汽由参数设置，不使用发电仓额定容量反向限流。流程为：

1. 周期耗汽预算由 Edit Parameters 设置，空控制器槽不阻止启动或运行。
2. 每升能量直接使用所选蒸汽的基础 EU/L，不乘转子效率。
3. 周期耗汽预算先转换为 L/t，再乘有效 EU/L 得到理论满负荷 EU/t，不封顶到发电仓额定；低供汽使用实际耗汽对应的 L/t 核算，启动倍率只降低电力。超过额定送出能力的电量直接作废，不缓存、不返还蒸汽、不降低耗汽。
4. 实际消耗蒸汽加冷凝余量，每 160 L 产生 1 L 蒸馏水，剩余 0—159 L 跨周期保存；水回收不受启动倍率影响。
5. 每 20 tick 扫描一次输入，实际耗汽取参数预算、输入库存与冷凝输出 int 防溢出约束的最小值，不再使用每 tick 十亿升或每周期 200 亿升界限。单批冷凝采用一个 `FluidStack`，因此保留 `(Integer.MAX_VALUE×160−冷凝余量)` 的数值安全界限；这不是动力仓性能上限。库存汇总与逐堆栈消费使用 long，批次转换为 tick 速率后计算 EU/t，电力逐 tick 送出。即使本批尚不足一升水，也预先核验一升水出口容量；批次水量放不下时拒绝且不消费，不缩减批次。没有蒸汽就不发电。

### 涡轮时间单位约定

涡轮运行计算以 **tick** 为速率基准；20 tick 仅为物料事务周期，不是功率单位。整数升数仅用于库存、扣料、冷凝及参数预算，不能直接传入功率计算。

| 数量 / 入口 | 单位与含义 |
| --- | --- |
| `steamLimitLitresPerCycle`、`effectiveSteamLimitLitresPerCycle`、`steamLitresPerCycle`、`waterLitresPerCycle` | L/周期；分别为设置上限、安全上限、实际耗汽批量、实际回收水批量 |
| `condensationRemainderLitres` | L 蒸汽；已消费、尚不足转换一升水的余量，不是流量 |
| `ProcessingCycleMath.litresPerTick(litresPerCycle, cycleTicks)` | 唯一的涡轮批次到速率转换入口，返回 L/t；保留不足整数升/t 的小数 |
| `inputLitresPerTick`、`outputLitresPerTick` | L/t；批次平均耗汽与实际整数水产出速率 |
| `SteamTurbineMath.generationEUt(steamLitresPerTick, euPerLitre)` | L/t × EU/L → EU/t；不再接收批次升数或周期时长 |
| `fullLoadEUt`、`operatingEUt` | EU/t；分别使用耗汽安全上限和实际耗汽量计算，均未乘启动倍率 |

## 启停、输出事务与存档

`StartupProgress` 为 0—1 的线性启动／衰减状态，不是温度或热缓存。供热与涡轮逐服务器 tick 推进，停机衰减，结构拆除清零；直发不预热。首次结构检查与邻近区块未加载时暂停处理，不因等待而衰减或清零；各机器检查范围见结构表。

公共层使用父类的正常周期推进和重检路径，`checkProcessing()` 统一设置 20 tick。发电返回 `GENERATING`，非发电成功返回 `SUCCESSFUL`；缺燃料、物品／流体出口满使用 Registry 现有结果，专有错误使用已注册的 `SimpleCheckRecipeResult` 及双语 `GT5U.gui.text.recipe_result.*` 键。`onRunningTick()` 只送电与推进启动，不扫描物料；组件伤害为零。

输入使用 GT 事务引用，ME 物品按标识去重并保留遍历顺序，公共流体消费按引用去重；双输入接口通过 `getAllItems()` / `getAllFluids()` 接入，仍受结构区域限制。DEBUG 输入沿用上游虚拟供给语义；不重复调用 GTNL 注入父类的双输入事务。

输出先经 `FluidEjectionHelper` 模拟预留：公共出口使用同一 helper，热交换 B/F 分组各用一个。父类 `startRecipeProcessing()` / `endRecipeProcessing()` 包住消费，确认成功后提交全部回调；事务不跨 tick、不落盘，父类产物数组为空以防重复输出。ME 抽取失败时不提交产物或发电，核燃料恢复快照；上游可能已扣部分物料，不承诺跨网络完整回滚。结束后更新并标记输入仓室脏状态。

发电通过 GT 继承的 `addEnergyOutput(long)` 入口送出，该入口调用 `addEnergyOutputMultipleDynamos(long, true)`，统一处理普通与扩展动力仓；本模组不覆盖这两个函数、不直接调用 `increaseStoredEnergyUnits`。本项目 `.133` 的多动力仓函数在请求超过总额定容量时爆炸，内部注入计数使用 `int`，因此请求先取实际产电、有效动力仓额定总量与 `Integer.MAX_VALUE` 的最小值。这是旧 GT API 的安全限额，不是最终平衡数值。

GT 返回布尔值不等于实际送出 EU：逐仓调用前后储能正增量之和为 `sentEUt`，产电减送出为 `discardedEUt`；它们统计进入仓室的能量，不是外部电网接收量。分配与能量包行为交给 GT，不承诺满仓份额重分配。送不出的整 EU 作废，燃料／蒸汽仍消费；没有真实 EU 缓冲，仅保留亚 EU 取整余量，出口全堵或作废时连同余量丢弃。全堵时即使不足整数 EU 也告警，恰好填满且全送出不误报。

| NBT | 保存内容 |
| --- | --- |
| 公共状态 | 启动进度、亚 EU 余量、结构标记、带版本的 20 tick 周期进度、已付费周期 EU/t、启动推进标志与显示速率；无真实 EU 缓冲 |
| 核电状态 | 模式、数量为 1 的完整燃料／乏燃料代表堆栈、独立整数批次数量、寿命小数、蒸馏水产汽小数余量、所选路径及反应堆热缓存；世界存档另保存满负荷产热显示速率 |
| 涡轮状态 | 0—159 L 冷凝余量、long 型周期耗汽参数；世界另保存当前燃料类型和有效周期上限；旧转子指纹不再使用，已有槽内物品仍由 GT 库存保存 |
| 热交换状态 | 当前热冷却液配方、所选蒸汽类型、四种蒸汽的小数余量、共用水耗额度；控制器物品保留额度和蒸汽余量 |

`Count` 为有符号字节，燃料以数量 1 的完整代表堆栈加独立整数数量保存，读取范围 1—2048；旧存档缺少数量键时从堆栈恢复。非法数量拒绝，小数校验、进度限幅，缺省为零启动与直发模式；热缓存读取时限于 0—`Integer.MAX_VALUE`，非有限值归零，不按尚未重检的结构等级截断，事务回滚亦保留降级前热量。仅版本匹配、有效的 20 tick 周期可在重载后续跑，产物不重复输出，旧一 tick 周期清空。关闭取消未送电力，不返还预付燃料／蒸汽；拆机物品携带核燃料状态及涡轮冷凝余量，不携带启动进度或周期电力。

核电产汽余量使用 `tnDistilledSteamRemainder`，合法范围为 `[0,1)`，旧存档缺失时为零。旧 `tnCoolantFraction_*` 与 `tnDistilledWaterFraction` 不再读取或写入：旧实现未将它们用于冷却计算，不能将其当作新的蒸汽余量迁移。未完成的整数升冷却转换保留的是 `tnReactorHeat` 中的热量。`tnFullLoadHeatRate` 仅用于世界存档恢复运行中显示，不随控制器物品携带。

### GUI info 字段与状态样式

三个具体 GUI 由各主机 `getGui()` 返回，`gui/ThermonuclearMultiblockGui.java` 提供终端布局与只读同步，保留启停、控制器物品槽、结构诊断和停机原因；涡轮物品槽不再承担转子功能，保留以便取出旧物品。`displayKeys()` 为固定字段全集，`displayInfo()` 为可见字段映射；按 `tnLine_<字段名>` 注册无 setter 的 `StringSyncValue`，空字符串隐藏并由 `collapseDisabledChild()` 收起，切换模式无须重开。`formatInfo()` 统一翻译与格式，`getInfoData()` 使用同一映射。

终端不列发电仓额定、送出、作废数值或涡轮冷凝余量。流体速率以 L/t 显示，最多三位小数、去尾零、千位分隔；涡轮周期参数用完整十进制 long 显示。热交换水耗显示本批实际取水量除以 20 tick，使用已有额度的批次可为零。状态颜色为运行绿、停机灰、等待黄、作废金、错误红，等级加粗；GT 事务失败细节仅在兜底失败状态显示，已知错误不重复叠加。标签灰、值青、模式金，中英文键一致。

核电的满负荷产热以热量/t 表示；满负荷热冷却液流量为产热速率乘所选冷却液的 L/热量比例，满负荷蒸馏水消耗为产热速率乘 `nuclearDistilledWaterPerHeat`。实际冷却液／水消耗和热流体／蒸汽输出分别取本批实际输入、输出升数除以 20；蒸汽输出包含小数余量的本批结算，不直接等同于水耗。满负荷流量是理论值，实际吞吐仍受热缓存、输入库存及出口容量限制。

Waila 通过服务端 NBT 显示核电／涡轮的产生和送出 EU/t，停机为零；热交换不显示发电信息。GUI 显示不替代物料、供热或送电结果验收。

## 原型配置

配置入口为 `CommonProxy.preInit()` 最先调用的 `Config.synchronizeConfiguration(event.getSuggestedConfigurationFile())`，使用 GTNHLib `0.11.51` 的 `ConfigurationManager.registerConfig(Config.class)`。文件保持 `config/thermonuclear.cfg`，参考 GTNL 的嵌套配置对象，以空根分类承载四个独立分组；不是 `prototype` 下的子组。不同于 GTNL 在 early coremod 注册，本项目仅在 preInit 注册，所有方块与机器注册及运行均在其后。

| 分组 / 文件分类 | 源码入口 | 配置归属 |
| --- | --- | --- |
| 通用 / `general` | `Config.general` | 问候语 `greeting`；非主机专属配置归入此组 |
| 核电站 / `nuclear_power_plant` | `Config.nuclearPowerPlant` | 15 项：效率、缓存、自然散热、燃料消耗及批量、冷却转换、输出倍率、启停进度 |
| 热交换站 / `heat_exchange_station` | `Config.heatExchangeStation` | 源码保留空分组，无生效字段；旧水耗与蒸汽倍率键不再读取或生成，不改变固定换热公式或开放超超临界生产 |
| 大型蒸汽涡轮机 / `large_steam_turbine` | `Config.largeSteamTurbine` | 2 项：启停进度；旧转子效率与流量倍率键不再读取或生成，耗汽上限仍为每台机器的 GUI／NBT 参数，不是全局配置 |

加载注解前先读取同一配置文件：将旧 `prototype` 内的已声明数值键迁移到对应机器分类，目标分类中已存在的键优先，随后移除旧分类；`general.greeting` 保持原位置。配置项名称、类型、默认值和范围均不改变。迁移只调整配置文件，不改机器 NBT。首次运行无文件时直接由注解生成新分组；重启已迁移配置时不再次迁移。

配置字段不写初始化值，默认值仅定义在 `@DefaultInt`、`@DefaultDouble`、`@DefaultString`；说明与单位用 `@Comment`，范围用 `@RangeInt`、`@RangeDouble`，字段名与旧配置键不同的项目用 `@Name` 保留兼容。加载前字段仍为 Java 的零值或 `null`，不得在静态初始化或更早的生命周期读取。以下数值仅为原型默认值，不是最终平衡。

源码开关 `Config.useDevelopmentDefaults` 默认为 `true`，标记 `@Ignore`，不写入 `.cfg`。仅当该开关为真且 `Launch.blackboard` 中 `fml.deobfuscatedEnvironment` 为真时，启动加载会递归将四组已声明配置项恢复为注解默认值、同步运行字段并覆盖保存（包括刚迁移的值）；修改默认值后重新启动开发客户端或服务器即可使用新值。将开关改为 `false` 后开发环境正常读取保存值，正式混淆环境不执行默认值覆盖。覆盖仅作用于本模组配置，不重置机器 NBT，不提供运行中热更新。

GTNHLib `0.11.51` 的 double 范围元数据不等同于数值限幅；本项目加载后递归校验实例字段，将非有限值回退到注解默认值、将越界值限制到注解范围，并回写所有配置字段。整数范围由库加载处理。四组配置均继承根类的需要重启标记，分类标题提供中英语言键；GTNHLib 会清理未声明的旧配置键和分类。当前格式、配置元数据静态对比与缓存 API 检查已通过，完整模组编译、真实旧文件迁移、开发默认覆盖和配置显示尚未验收。
