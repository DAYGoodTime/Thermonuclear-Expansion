## 范围与入口

需求依据是用户提供的 OpenChamber「Thermonuclear 第一阶段原型实现任务」及会话中的 ID 批准。仓库未跟踪的 `plan/` 属于用户工作，本次没有修改。产品 EV 阶段背景见 [Plan-01](../../../plan/Plan-01.md)，原稿冲突未改动。

`src/main/java/com/lin/thermonuclear/Thermonuclear.java` 转发 Forge 生命周期：

1. `CommonProxy.preInit()` 读取 Forge 配置。
2. `CommonProxy.init()` 调用 `loader/MachineLoader.register()`；在 GT 加载阶段构造三个 MetaTileEntity。
3. `CommonProxy.loadComplete()` 调用 `registry/WorkingFluids.resolve()`；所有模组材料加载完成后引用现有流体，缺失时记录错误，对应处理路径拒绝运行。

控制器物品由 `MachineLoader.nuclearPowerPlant`、`heatExchangeStation`、`largeSteamTurbine` 引用，均为 GT 机器物品。没有生存制造配方。

所有当前注册的控制器物品通过 `registry/ModItems.register(ItemStack)` 添加本模组标识：英文 `Thermonuclear Expansion [thermonuclear]`，中文同时显示“热核扩展”。后续注册本模组物品时也通过该入口添加标识。实现调用已有 GTNHLib `0.11.51` 的 `AnimatedTooltipHandler.addItemTooltip`，按物品和准确元数据匹配，不使用通配元数据，因此不会给其他模组共享的 GT 机器物品加标识；数量和 NBT 不影响识别。翻译在提示显示时读取，无须修改物品 NBT 或注册名。

实际解析的 NEI 为 `2.8.130-GTNH`，已核对其 `TooltipFilter` 和 `NEIClientConfig` 源码：提示词搜索读取物品 tooltip，默认前缀为 `#`。启用 NEI 提示词搜索后使用 `#thermonuclear`；开启无前缀提示词搜索时也能直接搜索 `thermonuclear`。该标识不改变 GT 物品的注册归属，不把模组归属搜索当作 tooltip 搜索。

## 结构与仓室

结构集中于 `machine/PrototypeMultiblockBase.java`：`BOX_SIZE=3`，偏移 `(1,1,0)`；控制器位于前面正中、第二层。26 格外壳中的一格是控制器，剩余 25 格使用 `Casings.HeatProofMachineCasing`，允许相关仓室替换；内部一格严格为空气。`construct()` 提供 StructureLib 提示，`checkMachine()` 使用当前 GT 错误列表接口。

`SHAPE` 使用 StructureLib 原生顺序 `[深度][从上到下的行]`，直接传给 `addShape`，不再转置。`~` 位于 `(1,1,0)`，由 StructureLib 跳过已有主机；`-` 位于 `(1,1,1)`。旧代码再次 `transpose` 将 `~` 移到 `(1,0,1)`，使主机原位置成为外壳位置，构建预览会覆盖主机并影响材料统计。修复轴向，不把 `~` 注册成额外放置元素、不增加第 26 个外壳。双语结构说明明确每个仓室替换一个外壳，而非额外添加。

本次只读参考 GTNL 的 `common/machine/multiblock/steam/LargeSteamAlloySmelter.java`（结构和偏移）、`common/machine/multiblock/ResourceCollectionModule.java`（可选仓室外壳）、`loader/MachineLoader.java` 和 `utils/text/AnimatedTooltipHandler.java`（按物品注册品牌 tooltip）。GTNL 从资源读取的结构与本项目内联数组的轴顺序分别核对，不能机械套用 `transpose`；GTNL 自有动画处理器不迁入，使用本项目实际已有的 GTNHLib API。StructureLib `1.4.42` 的 `transpose`、`StructureDefinition.Builder.addShape` 和 GT5U `.133` 的外壳放置实现已核对源码 JAR。

原型支持多个普通 GT **实体标准仓室**，按准确类接入 `MTEHatchInput`、`MTEHatchOutput`、`MTEHatchInputBus`、`MTEHatchOutputBus`、`MTEHatchDynamo`。ME、销毁、维护、自定义与其他派生仓室不在本阶段适配范围。

| 机器 | 结构 / 运行要求 |
| --- | --- |
| 核电站 | 结构要求物品输入和输出仓；直接发电另需有效发电仓；供热另需流体输入和输出仓 |
| 热交换站 | 流体输入和输出仓 |
| 涡轮 | 流体输入、流体输出、发电仓；控制器内一件有效 GT 转子 |

关闭 `shouldCheckMaintenance()`，固定满维修状态并修复工具标志；没有维护效率损失。涡轮仍调用父类 `doRandomMaintenanceDamage()`，保留 GT 的组件检测、1000 tick 计数、随机触发、伤害系数和工具耐久 NBT，组件伤害参数沿用普通蒸汽涡轮的 `1`。没有另写磨损公式。

## 燃料适配与核电模式

适配边界为 `nuclear/FuelRodAdapter.java`；只读取有效 IC2 / GT 燃料类，不将任意 `IReactorComponent` 当作燃料。

| 来源 | 已核验语义 |
| --- | --- |
| IC2 铀单/双/四联 | `ItemReactorUranium.numberOfCells` 为 1/2/4；最大自定义耐久 20000；`advDmg` 储存已用周期；对应三个 `Ic2Items.reactorDepletedUranium*` |
| IC2 MOX 单/双/四联 | `ItemReactorMOX`；最大自定义耐久 10000；同一耐久 API；对应三个 `Ic2Items.reactorDepletedMOX*` |
| GT 燃料棒 | `ItemRadioactiveCellIC` 的单/双/四联；读取 `sEnergy`、`sHeat`、最大自定义耐久及 `sDepleted`；调用父类耐久访问/修改 API |

IC2 反应堆 `getTickRate()` 为 20，一单位燃料寿命是一秒的反应周期，而不是一个游戏 tick。`getOfferedEnergy()` 和 GT 燃料描述使用 `5 × balance/energy/generator/nuclear` 的 EU 输出转换，不使用 GTNL 的 `25`。

自脉冲数为 `1 + cells/2`。电力基准来自燃料自身无邻接属性；热属性为每个燃料周期的自脉冲三角数乘热系数，GT 按每个子棒分别取整。没有温度模型，MOX 不获得温度加成；没有邻接、反射板或布局收益。冷热流体的测试换算是本模组配置，不声称复刻 IC2 液冷反应堆的全部热交换物理。

继承这些已核验类且没有覆盖相关反应、耐久、乏燃料方法的派生类允许使用；覆盖这些方法的第三方实现明确拒绝。GTNL 自有 FuelRod 等未知实现未适配。适配类名称不能作为“所有燃料均兼容”的证据。

`MTENuclearPowerPlant` 从普通输入仓提取一根燃料并复制完整 NBT，输入堆栈其余物品不磨损。当前燃料与小数寿命余量独立保留：

- `DIRECT_GENERATION`：正常消耗寿命，效率较低；启动倍率只作用于产电，不访问冷却液。
- `HEAT_SUPPLY`：同一个启动倍率作用于燃料周期消费，再由此计算冷却液消费与等量热冷却液输出，不再次乘启动倍率；不产电。
- 模式为枚举，效率通过 `NuclearEfficiencyPolicy` 的配置实现读取；没有电路板物品或槽位。
- GUI 模式按钮走服务器回调；必须先关闭机器，服务器检查 `isAllowedToWork()` 和运行状态，拒绝运行中切换。切换不改变燃料、寿命、余量或待输出产物。
- 乏燃料输出采用 GT 物品事务。容量不足时保留单根待输出棒，阻止取用下一根燃料；它不进入父类自动清空的 `mOutputItems`。
- 供热不足整数升时仍推进启动和燃料小数进度，但先检查至少一升对应冷却液及热流体出口；真正提交的冷/热流体数量严格相等。

## 热交换与蒸汽涡轮

`registry/WorkingFluids.java` 使用 `Materials.Steam`、GT 的 IC2 蒸馏水/冷却液访问器、`Materials.SuperCoolant` 和 `WerkstoffMaterialPool.HotSuperCoolant`，不猜测超级冷却液注册名，不新增流体。

`recipe/HeatExchangeRecipe.java` 提供两条独立路径：IC2 热冷却液、热超级冷却液各自配合蒸馏水，输出普通 GT 蒸汽与等量对应冷却液。每周期仅选一条；配置以“热冷却液升数／每升水”的正整数定义有效收益。消费热冷却液采用该比值的整倍数，工作流体与蒸汽按 `GTValues.STEAM_PER_WATER=160` 换算，不需要热交换小数缓冲。处理周期期间不预先消费，周期结束才联合提交。输出堵塞时取消周期推进，零消费；无热源不产汽。

涡轮使用 `MetaGeneratedTool01` 的 GT 转子元数据 170—179及 `TurbineStatCalculator`。实际蒸汽流体必须是 `Materials.Steam` 的实例，其他蒸汽等级或无关混入流体保持不变。转子流量属性仅作为有界容量，不作为最佳流量要求。流程为：

1. 转子蒸汽流量乘本模组容量倍率，限制实际吞吐。
2. 转子效率乘本模组效率倍率并封顶 1，保证普通蒸汽原始能量上限为 `0.5 EU/L`；不更改转子物品全局属性。
3. 转子和发电仓额定容量共同限制满负荷输出，低供汽仅按实际消耗量核算；启动倍率只降低电力。
4. 实际消耗蒸汽加冷凝余量，每 160 L 产生 1 L 蒸馏水，剩余 0—159 L 跨周期保存；水回收不受启动倍率影响。
5. 即使本 tick 尚不足一升，也预先核验一升水出口容量。没有蒸汽就不发电。

换转子检测包含实时物品对象、更换/移除槽位的 `onContentsChanged()` 和保存的转子指纹。指纹排除 `GT.ToolStats.Damage`，GT 自身磨损不清空启动进度；区块重载后使用已保存指纹匹配。损坏、移除或真正更换时清零。

## 启停、输出事务与存档

`StartupProgress` 提供共享的线性推进与衰减规则；核电与涡轮分别持有实例与配置。按服务器 tick 更新，范围 0—1，不是温度或蓄热。正常运行升高，停机衰减；拆除成型结构清零。首次结构检查及相邻区块未加载时暂停处理，不因等待加载衰减或清零。原型用控制器周围半径 2 的保守区块包围范围，覆盖盒子的所有朝向。

公共基类替换父类 `runMachine()`，不让父类再消费一次输入、提交一次产物或储存发电缓冲。联合输出使用一个 `FluidEjectionHelper` 的事务集合，同时模拟全部产品后才消费输入并 `commit()`，防止同一空槽被多种产物重复计入容量。这些事务不跨 tick、不落盘：提交前没有输入变化，所以没有半批次流体需要保存。

发电逐个物理发电仓提交，每 tick 同时限制 `maxEUOutput × maxAmperesOut` 和剩余储存空间；不调用会因越界爆炸的无限额输出路径。不能容纳的整 EU 作废，不影响燃料或蒸汽正常消耗；没有真实 EU 缓冲。只有小于 1 EU 的取整余量，出口全满或出现作废电力时也丢弃该余量。显示理论满负荷、发电仓额定上限、爬升后的整数产电、送出和作废电力；供热模式另显示满负荷热冷却液 L/t。即使本 tick 产电不足整数 EU，出口完全受阻也显示输出受限。

| NBT | 保存内容 |
| --- | --- |
| 公共状态 | 启动进度、小于 1 EU 的取整余量、此前结构成型标记；不保存真实 EU 缓冲 |
| 核电状态 | 枚举模式、完整工作燃料堆栈、燃料小数消费、两种冷却液各自余量、所选冷却液、待输出乏燃料 |
| 涡轮状态 | 0—159 L 冷凝余量、排除磨损的转子指纹；转子与耐久由 GT 库存保存 |
| 热交换状态 | 当前配方及未消费输入的周期进度 |

旧 NBT 缺失值使用零进度和直接发电模式，非法小数余量/进度归零或限制范围。加载时清空父类的旧配方进度、产物数组和 EU/t，避免恢复旧缓冲。核电内部燃料和待输出乏燃料写入控制器物品 NBT，涡轮也携带冷凝余量；拆下重放不带启动进度或电力。

`machine/PrototypeGui.java` 在当前 GT 默认 ModularUI2 界面的可滚动终端中追加数据；保留 GT 默认启停和转子槽。显示状态、启动、产出、输入/输出、模式或配方、燃料/转子及停机原因。数据使用无 setter 的 S2C 同步值，客户端不能修改燃料或余量；模式按钮仅发送交互请求。`getInfoData()` 也提供相同信息。中文/英文语言资源均使用 `thermonuclear` 键。

## 原型配置

配置加载入口是 `src/main/java/com/lin/thermonuclear/Config.java`，Forge 的 `prototype` 分类标明测试默认值。有限数值、正周期和范围在加载时验证并回写；直接发电效率必须低于供热效率，否则调整为供热效率的一半。

| 配置键 | 测试默认值 | 单位 / 范围 |
| --- | --- | --- |
| `nuclearDirectEfficiency` | 0.25 | 0.001—1，且小于供热效率 |
| `nuclearHeatEfficiency` | 1 | 0.001—1 |
| `fuelCyclesPerSecond` | 1 | 寿命周期/秒，0.001—100 |
| `ic2CoolantLitresPerFuelHeatUnit` | 1 | L/燃料属性热单位，0.001—1000 |
| `superCoolantLitresPerFuelHeatUnit` | 0.25 | 同上 |
| `exchangeHotFluidPerCycle` | 100 | L/处理周期，1—1000000 |
| `exchangeCycleTicks` | 20 | tick，1—72000 |
| `ic2HotCoolantLitresPerWater` | 1 | L 热流体/1 L 水，1—1000000 |
| `hotSuperCoolantLitresPerWater` | 1 | 同上 |
| `rotorEfficiencyMultiplier` | 1.5 | 1—100，最终实际效率封顶 1 |
| `rotorCapacityMultiplier` | 2 | 1—100 |
| `nuclearStartupTicks` / `nuclearDecayTicks` | 1200 / 600 | 从 0 到 1／从 1 到 0 的 tick 数，1—720000 |

例如默认单根 IC2 铀棒无邻接基准是 `5 × IC2 核电配置倍率 EU/t`、4 个属性热单位/燃料周期。供热模式将它换算为配置规定的冷热流体，换热站再据另一组测试配置消费蒸馏水。这个例子解释单位，不是已验收的链路守恒或最终能源平衡。
