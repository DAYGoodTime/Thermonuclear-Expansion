# 操作规则

## 归档规则

### 归档触发条件

- 文档状态变为终态 → 归档
- 文档状态变为「已废弃」→ 归档
- feature 实现完成后，该 feature 下需求/设计/实现规划等相关文档进入终态 → 归档
- wiki 文档被终态化、失效、拆分替换，或翻新时正文移除了旧内容 → 归档
- ADR 状态变为「已废弃」或「已取代」→ 归档
- 文档内容与项目当前方向不符 → 归档
- 其他情况视具体情况决定是否归档

feature 终态包括但不限于：`已完成`、`已实现`、`已废弃`、`已搁置`。

ADR 的「已采纳」不是归档触发条件。已采纳 ADR 是活跃架构决策，必须保留在 `{DOC_ROOT}/adr/` 供后续开发查阅；只有状态为「已废弃」或「已取代」的 ADR 才归档。

wiki 默认长期有效，不因“完成”归档；只有确认失效、被替代、被拆分，或翻新时正文移除了旧内容，才归档。

### 归档操作

归档文件必须移动到**对应分类目录下**的 `archive/` 文件夹，并保持可追溯结构：

```
features/
├── archive/
│   └── 2026-01-15-某功能/
│       ├── 1-需求.md
│       ├── 2-设计-xxx.md
│       ├── 3-实现.md
│       ├── 4-内容变更说明.md
│       └── 参考/
│           └── 100-某调研.md
└── 2026-02-20-进行中的功能/

adr/
├── archive/
│   └── ADR-0003-已取代的决策.md
└── ADR-0004-进行中的决策.md

wiki/
├── architecture/
├── development/
├── operations/
└── archive/
    ├── architecture/
    │   └── 旧架构说明.md
    └── development/
        └── 已失效开发流程.md

archive/
└── misc/
    └── 无明确分类的历史文档.md
```

1. feature 完成/废弃/搁置等进入终态后，整个 feature 目录移入 `{DOC_ROOT}/features/archive/`，不再留在 `features/` 活跃根目录。
2. wiki 文档失效、被替代、被拆分或正文移除内容后，移入 `{DOC_ROOT}/wiki/archive/` 下对应主题目录或创建归档摘录。
3. ADR 状态为「已采纳」时保留在 `{DOC_ROOT}/adr/`；状态变为「已废弃」或「已取代」后，移入 `{DOC_ROOT}/adr/archive/`，不再留在 `adr/` 活跃根目录。
4. 只有无明确分类的历史材料，才放入 `{DOC_ROOT}/archive/` 下的全局 archive。
5. 如果只是从文档中移除一段失效内容，创建归档摘录文件，记录来源文件、原章节、移除时间、移除原因和原文。
6. 更新 `{DOC_ROOT}/README.md` 索引，从活跃索引中移除或标注归档位置。
7. 不删除文件和移除内容，必须保留历史记录。

## README 索引规则（强制）

1. `{DOC_ROOT}/README.md` 的功能文档索引按创建日期降序排列，最新 feature 放在最上方。
2. 同一天多个 feature 按目录名自然排序。
3. 新增、归档、重命名 feature 或 feature 内文档时，必须同步更新 README 链接。
4. README 中不得保留指向不存在文件的链接。
5. 终态且已归档的 feature 不应继续留在活跃功能索引中；如需要保留入口，应明确标注归档路径。

### 失效内容归档摘录格式

当翻新文档时移除正文中的失效内容，创建类似文件：

```text
wiki/archive/development/2026-05-26-开发环境搭建指南-移除内容.md
features/archive/2026-05-26-某功能/2026-05-26-实现-移除内容.md
```

内容模板：

```markdown
# [原文档标题] 移除内容归档

> 移除时间: YYYY-MM-DD HH:mm
> 来源文档: ../path/to/source.md
> 原章节: xxx
> 移除原因: 已失效 / 被新方案取代 / 与当前项目方向不符

## 原文

...
```

## 图片与资源文件

所有图片、截图、架构图、流程图等资源文件统一放入 `{DOC_ROOT}/assets/`。

### 命名规范

```
assets/
├── {功能名}-{描述}.{ext}          ← 功能相关资源
├── wiki-{文档名}-{描述}.{ext}     ← wiki 相关资源
└── adr-{编号}-{描述}.{ext}        ← ADR 相关资源
```

示例：
- `assets/日志系统改造-架构图.png`
- `assets/wiki-项目架构概览-分层示意.svg`

### 引用方式

在文档中使用相对路径引用：

```markdown
![架构图](../assets/日志系统改造-架构图.png)
```

## 创建前查重（强制）

新建 feature 文档前，必须先检查 `{DOC_ROOT}/features/` 下是否已有同名或相似功能的文档。新建 ADR 或 wiki 时，应检查对应目录下是否已有相同主题文档，避免重复记录全局决策或长期知识。

查重的目的不是复用旧 feature，而是：

- 给新文档添加关联参考链接
- 判断旧文档是否已经过期、应标记终态或归档
- 避免重复命名导致读者误解

**强制规则**：每次用户提出新的产品需求、业务功能、用户可见能力、具体功能方案、具体功能计划、具体功能实现记录或功能参考沉淀时，不论内容是否与旧文档相关，都必须创建新的日期编号 feature 目录。旧 feature 不作为新内容的默认写入目标。全局技术选型、架构基线、基础设施选型、开发规范、工具链、部署运维、排障经验不创建 feature，应写入 ADR、wiki 或 conventions。

### 查重流程

1. 搜索 `features/` 目录名和文档标题，匹配关键词
2. 如果发现相似文档 → **继续创建新 feature**，并在新文档中按需加入「相关文档」链接；必要时向用户提示：
   - 已有文档的路径
   - 已有文档的状态
   - 已有文档的概要内容（标题 + 目标/背景段落）
3. 不询问“是否翻新旧文档”。只有用户明确要求修改旧文档时，才允许更新旧 feature；否则新内容一律写入新 feature。
4. 如果旧文档明显不再符合当前方向，可询问是否归档旧文档；归档与新建 feature 是两个独立动作。

## Feature 内文档排序规则（强制）

### 命名格式

`features/YYYY-MM-DD-功能名/` 目录内的 Markdown 文档必须使用数字前缀：

```text
1-需求.md
2-设计-标题.md
3-实现.md
4-内容变更说明.md
```

`参考/` 子目录内的参考文档使用独立编号段，从 `100-` 开始：

```text
参考/100-接口调研.md
参考/101-竞品分析.md
```

### 排序语义

1. 数字前缀表示文档创建时间顺序，从早到晚递增。
2. 同一轮同时创建多个 feature 根目录文档时，按需求、设计、实现、内容变更说明的顺序编号。
3. 后续新增文档时，使用当前 feature 目录中最大编号加 1。
4. 不要为了插入新文档而重命名旧文档；旧文档编号是历史创建顺序的一部分。
5. 更新旧文档内容时不改变文件名编号，不添加或刷新更新时间字段；修订记录遵循项目规则。
6. 参考文档不占用 feature 根目录编号，统一放在 `参考/` 子目录并从 `100-` 开始递增。
7. Feature 根目录编号空间为 `1-` 到 `99-`，`100-` 起仅用于 `参考/` 子目录。
8. 不在 feature 根目录创建 `100-*.md`，不在 `参考/` 子目录创建 `1-*.md`。

### 新建前检查

在已有 feature 目录中新建文档前，必须先列出该目录现有 `N-*.md` 文件，确定下一个编号。

在已有 `参考/` 子目录中新建参考文档前，必须先列出该目录现有 `100-*.md`、`101-*.md` 等文件，确定下一个参考编号。

### 重命名旧文档

只有用户明确要求“整理/重命名旧 feature 文档”时，才允许批量重命名旧文档。重命名前必须：

1. 列出旧路径和新路径映射。
2. 更新 README 和文档间相对链接。
3. 搜索并更新引用旧路径的 Markdown 链接。
4. 不改变文档头部的「创建日期」。
5. 在被修改文档或 README 的修订记录中说明重命名原因。

### 提示格式

```
发现已有相似文档：

[文档] features/2026-03-20-商户使用情况统计/需求.md
   状态: 草稿
   概要: "统计各商户的日活、消息量等使用数据..."

处理方式：
1. 继续创建新的 feature 文档，并在「相关文档」中链接上述文档
2. 如旧文档已不符合当前方向，可另行确认是否归档
```

## 新 Feature 优先规则（强制）

### 默认规则

以下情况必须创建新的 `features/YYYY-MM-DD-功能名/` 目录：

- 用户提出新的产品需求、业务功能、用户可见能力或具体功能想法
- 用户要求记录某个具体功能的规划、设计或实现安排
- 用户要求记录某个具体功能的本次实现、审查、调研、参考资料或后续计划
- 当前内容与旧 feature 有关联，但目标、范围、时间点、实现阶段或结论已经变化
- 旧 feature 已经完成/已实现/已采纳/已废弃/已搁置

以下情况不创建 feature，应按主题进入 ADR、wiki 或 conventions：

- 全局技术选型、语言/框架/数据库/队列/部署选型
- 跨功能架构基线、系统边界、基础设施选型
- 长期开发指南、目录结构、编码规范、工具链、开发环境
- 部署运维、监控告警、排障经验、运行手册
- 跨项目调研、技术对比、参考资料

### 不创建新 Feature 的情况

以下情况不创建新的 feature：

1. 用户明确要求修改 skill、模板、规范、README、wiki、ADR 或已有文档。
2. 用户要求修正刚创建文档的命名、格式、状态、错别字、链接或索引。
3. 用户是在补充同一轮文档创建约束，且当前任务尚未结束。
4. 用户要求把新规则写入全局文档规范，而不是记录项目功能。
5. 代码改动只涉及格式化、测试补充、内部重构或不改变用户/API/部署/数据模型行为的微调。
6. 内容属于全局技术选型、架构基线、基础设施选型、开发规范、工具链、部署运维、排障经验或长期知识沉淀。

### 禁止事项

除非用户明确要求修改旧文档，否则禁止：

- 将新需求追加到旧 feature 的 `需求.md`
- 将新方案追加到旧 feature 的 `设计-*.md`
- 将新计划追加到旧 feature 的 `实现.md`
- 为了“保持集中”而翻新旧 feature
- 因为查重命中就停止创建新 feature

### 允许事项

- 在新 feature 文档的「相关文档」中链接旧 feature
- 在旧 feature 已经过期或方向不符时，按归档规则处理
- 用户明确要求“更新旧文档”时，按用户要求修改旧文档，并追加修订记录

## 文档质量检查清单（强制）

创建或更新文档后，必须自检：

1. 文档头部的创建日期、作者、状态或类型符合文档类型要求；不包含自动维护的「最后更新」等时间字段。
2. 文件名编号符合规则：feature 根目录使用 `1-99`，参考文档使用 `参考/100-*.md` 起。
3. README 索引已更新，且功能文档索引按创建日期降序排列。
4. 相对链接指向真实存在的文件或目录。
5. 没有 `[链接]`、`...`、`功能点 1`、`步骤一`、`path/to/file` 等模板占位符残留。
6. 修订记录已追加，时间格式为 `YYYY-MM-DD HH:mm`。
7. 文档内容没有记录未确认的备选方案，除非用户明确要求。
8. 文档长度与问题复杂度匹配，没有为了套模板保留空章节。

## 文档长度控制

1. 简单决策、调研、排查结论：300-800 字。
2. 普通技术方案：800-2000 字。
3. 跨模块改造、架构决策、复杂迁移：可超过 2000 字。
4. 不为了套模板补空章节；没有实际内容的章节应删除或合并。
5. 单个文档超过 600 行时，按「文档拆分」规则评估是否拆分。

## 代码改动后的文档影响判断

代码改动后，仅在以下情况更新 docs/wiki：

1. API 行为、请求/响应模型或错误语义变化。
2. 配置、部署、环境变量、任务调度或队列拓扑变化。
3. 数据模型、迁移、存储结构或数据保留策略变化。
4. 新增公共能力、脚本入口、开发约定或运维入口。
5. 修复会影响后续排障的线上问题。
6. 用户明确要求记录本次改动。

纯重构、格式化、测试补充、内部实现微调，默认不更新 wiki，只在最终回复中说明无文档影响。

## Feature 完成标记规则（强制）

### 触发条件

当某个 feature 对应实现完成，并且已经通过用户确认、验收、验证或实现任务结束时，必须同步更新文档状态。

### 状态更新要求

根据 feature 内文档类型更新为终态：

- 需求文档：`已完成`
- 技术方案：`已实现`
- 实现规划：`已完成`
- ADR：若决策已采用则为 `已采纳`，若被替代则为 `已取代`
- 参考文档：无状态流转，修订记录遵循项目规则，不更新最后更新时间

同时必须更新 `{DOC_ROOT}/README.md` 中功能索引的状态列：

- feature 全部实现完成 → 标记为 `已完成`
- 仅方案落地完成 → 可标记为 `已实现`
- 部分完成 → 明确写成 `部分完成` 或保留 `进行中/规划中`，不要含糊

### 修订记录

状态更新属于内容变更，修订记录遵循项目规则，不添加或刷新文档更新时间字段。

状态更新为终态后，必须立即按「归档规则」移动到对应分类 `archive/`：feature 到 `features/archive/`，ADR 到 `adr/archive/`，wiki 到 `wiki/archive/`。README 中索引应指向归档位置或从活跃索引移除，不能让终态文档继续显示为活跃待办。

## 修订记录

每个文档末尾必须维护修订记录，时间精确到分钟。

### 记录类文档的追加规则（强制）

- 适用于修订、开发验证、变更、交付等记录文档及文档内的历史记录区。
- 未经用户明确要求修改历史记录，只允许在文件或记录区末尾追加，不修改、删除、合并或重排已有记录，不在顶部插入。
- 发现旧记录有误时，追加简短更正并指明对应记录，不改写原记录。
- 新增记录简洁干净，只保留必要事实、关键结论与验证边界，不堆砌过程、重复说明、完整命令输出或无关细节。
- 当前事实型正文仍就地维护；本规则不将知识库、指南或规范正文改为追加日志。

### 格式

```markdown
---

## 修订记录

| 时间 | 作者 | 变更说明 |
|------|------|----------|
| 2026-04-27 14:30 | {git user.name} | 初始创建 |
| 2026-04-28 09:15 | {git user.name} | 补充边界条件处理 |
```

### 规则

- 文档首次创建时，添加「初始创建」记录
- 每次修改文档内容时，追加一行修订记录
- 时间格式：`YYYY-MM-DD HH:mm`
- 纯格式调整（如修正 typo、调整排版）可不记录
- 修订记录位于文档最末尾，用 `---` 分隔线与正文隔开

## Git 提交规则

### 默认行为：不提交文档

文档默认不纳入 git 版本控制。首次初始化 `{DOC_ROOT}` 时，将文档目录写入 `.git/info/exclude`（非 `.gitignore`）：

```bash
echo "{DOC_ROOT}/" >> .git/info/exclude
```

### 例外：项目已有文档在 git 中

如果项目的 git 仓库中已经存在 `docs/` 或 `dev-docs/` 目录且已被跟踪，则文档随代码一起提交，不写入 exclude。

判断方式：

```bash
git ls-files --error-unmatch {DOC_ROOT}/ 2>/dev/null
```

如果有输出（已跟踪文件存在）→ 文档跟随 git 提交。
如果无输出或报错 → 文档不提交，写入 `.git/info/exclude`。

## 文档拆分

### 何时考虑拆分

单个文档超过 600 行时，可以考虑是否需要拆分。这不是硬性规定，酌情处理即可。

参考信号：
- 文档中有 2 个以上相对独立的主题（各自可以单独阅读）
- 某个章节膨胀到占全文 50% 以上
- 不同章节的更新频率差异很大

内容虽长但逻辑连贯、拆开后需要频繁跳转的，不必拆分。

### 拆分方式

1. 按逻辑章节拆为独立文档，沿用现有命名模式：
   - 设计文档：`设计-子标题A.md` + `设计-子标题B.md`
   - 需求文档：`需求-子标题A.md` + `需求-子标题B.md`
2. 如果拆出的内容是参考性质，放入 `参考/` 子目录
3. 拆分后在各文档的「相关文档」中互相链接
4. 更新 README.md 索引

## 多方案写作规则（强制）

适用于需求文档、技术方案文档、实现规划文档。

### 默认规则

当存在多个可行方案时：

1. **先在对话中口头告知用户可选方案**
2. **等待用户选择或明确倾向**
3. **文档中只写入最终确认的方案**

### 禁止事项

在用户未明确要求的情况下，文档中**不得**默认写入以下内容：

- `备选方案` 章节
- `方案 A / 方案 B / 方案 C` 对比表
- “可选方案如下” 一类的罗列
- “推荐方案 / 次选方案” 一类的候选列表

### 例外情况

只有当用户明确表达以下意图之一时，才允许把多方案内容写入文档：

- “把几个方案都写进文档”
- “需要方案对比文档”
- “把备选方案也记录下来”

### 写作要求

如果用户没有明确要求记录多方案：

- 技术方案文档中只保留**已确认的单一方案**
- 实现规划文档中只保留**已确认方案对应的执行步骤**
- 不要为了“完整”而自动加入备选内容

## 过期检测

### 触发时机

每次 skill 被触发时（创建文档、更新文档、代码改动后更新 wiki），顺带扫描 `{DOC_ROOT}/features/` 和 `{DOC_ROOT}/wiki/`。

### 检测规则

通过 Git 历史查询所有**非终态**文档的最近内容修改时间，不为过期检测在文档中添加或刷新时间字段。未纳入 Git 或没有可用历史时跳过时间检测，不推测日期：

| 文档状态 | 过期阈值 | 说明 |
|----------|----------|------|
| 草稿 | 30 天 | 长期停留在草稿可能已被遗忘 |
| 评审中 | 14 天 | 评审不应拖太久 |
| 进行中 / 规划中 | 30 天 | 活跃工作不应长期无更新 |
| 已确认（未开始实现） | 60 天 | 确认后迟迟不动可能需要重新评估 |

终态文档（已完成、已实现、已采纳、已废弃、已搁置）不检测。

### 检测到过期时

向用户提示，不自动处理：

```
以下文档可能已过期：

[!] features/2026-02-10-用户统计/需求.md
    状态: 草稿 | Git 最近修改: 2026-01-15 (72 天前)

[!] wiki/API文档.md
    Git 最近修改: 2025-12-20 (128 天前)

建议：更新内容 / 推进状态 / 归档
```

用户可以选择忽略，不强制处理。
