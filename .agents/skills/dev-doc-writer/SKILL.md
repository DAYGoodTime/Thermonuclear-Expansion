# dev-doc-writer — 项目文档全流程管理

为任意项目提供标准化的文档管理能力，覆盖从想法记录到需求、设计、实现规划、ADR、参考文档的全流程。

## 与 product-requirements 的边界

当用户只有模糊想法、灵感、产品概念，且需要逐步追问澄清时，先使用 `product-requirements`。

当用户明确要求写入文档、创建需求/设计/实现规划、更新 README/wiki/ADR/changelog、或记录已明确的方案时，使用本 skill。

不要为了普通代码实现任务自动创建文档；只有用户要求文档，或代码改动对项目 wiki 有明确影响时才更新文档。

## 触发场景

| 用户意图 | 动作 |
|----------|------|
| 提出想法、灵感、点子 | 在 `features/` 下创建需求草稿，状态为「草稿」 |
| 描述需求、提功能要求 | 创建完整的需求文档 |
| 要求设计、出方案、做规划 | 根据文档路由规则创建功能设计、ADR 或 wiki |
| 要求计划实现、排任务、拆步骤 | 创建实现规划文档 |
| 要求记录决策 | 创建 ADR |
| 要求写参考文档/changelog | 创建对应文档 |
| 要求按文件说明本分支或本次代码改动 | 创建/更新 `内容变更说明.md` |
| **项目代码发生改动** | **同步更新项目 wiki（详见 @references/wiki-rules.md）** |

## 文档类型选择规则

当用户没有明确指定文档类型时，按以下规则选择：

1. 用户描述具体产品能力、业务功能、用户可见行为“要做什么 / 想实现什么 / 需要什么能力” → 创建 `features/YYYY-MM-DD-功能名/N-需求.md`。
2. 用户询问某个具体功能“怎么做 / 如何实现 / 功能技术方案” → 创建该 feature 下的 `N-设计-标题.md`。
3. 用户要求某个具体功能“拆任务 / 排期 / 计划实现 / 落地步骤” → 创建该 feature 下的 `N-实现.md`。
4. 用户要求跨功能、跨项目、全局技术选型、架构基线、基础设施选型、语言/框架/数据库/队列/部署选型 → 创建 ADR，不创建 feature。
5. 用户要求记录长期有效的开发指南、架构说明、模块说明、工具链、部署运维、排障经验 → 创建或更新 `wiki/`，不创建 feature。
6. 用户要求记录调研、对比、分析现状、排查结论、参考资料：若服务于某个具体 feature → 创建该 feature 下 `参考/100-标题.md`；若是跨项目通用资料 → 创建 `wiki/references/标题.md`。
7. 用户要求“总结本次改动 / 按文件说明 / 本分支做了什么 / 内容变更说明” → 创建或更新 `N-内容变更说明.md`。
8. 用户明确说“更新现有文档 / 修改某个文档 / 改刚才的文档” → 修改指定文档，不新建 feature。

### 文档路由表

| 内容类型 | 推荐位置 |
|----------|----------|
| 产品需求、业务能力、用户可见功能 | `features/YYYY-MM-DD-功能名/1-需求.md` |
| 具体功能技术设计 | `features/YYYY-MM-DD-功能名/N-设计-标题.md` |
| 具体功能实现计划 | `features/YYYY-MM-DD-功能名/N-实现.md` |
| 全局技术决策、架构决策、技术栈选型、基础设施选型 | `adr/ADR-NNNN-简短描述.md` |
| 架构说明、模块说明、开发指南 | `wiki/architecture/` 或 `wiki/development/` |
| 本地工具链、编码规范、开发约定 | `wiki/development/` 或 `conventions/` |
| 部署、监控、告警、排障、运行手册 | `wiki/operations/` |
| 跨项目调研、技术对比、参考资料 | `wiki/references/` |
| 某个具体 feature 的调研资料 | `features/YYYY-MM-DD-功能名/参考/100-标题.md` |
| 代码改动说明、按文件说明 | 对应 feature 下 `N-内容变更说明.md` |

当内容可能同时属于 feature、ADR、wiki 时，优先级为：ADR > wiki > feature。若仍无法判断，先向用户确认，不直接创建。

## 不创建新 Feature 的情况

以下情况不创建新的 `features/YYYY-MM-DD-功能名/`：

1. 用户明确要求修改 skill、模板、规范、README、wiki、ADR 或已有文档。
2. 用户要求修正刚创建文档的命名、格式、状态、错别字、链接或索引。
3. 用户是在补充同一轮文档创建约束，且当前任务尚未结束。
4. 用户要求把新规则写入全局文档规范，而不是记录项目功能。
5. 代码改动只涉及格式化、测试补充、内部重构或不改变用户/API/部署/数据模型行为的微调，默认不更新 wiki，只在回复中说明无文档影响。
6. 内容属于全局技术选型、架构基线、基础设施选型、开发工具链、部署运维、长期开发知识沉淀，应创建 ADR 或 wiki，而不是 feature。

## 优先级规则

**项目自身的文档 skill 优先。** 本 skill 仅在项目没有自己的文档规范/skill 时生效。

检查顺序：
1. 项目根目录下是否有 `.kiro/skills/`、`.agents/skills/` 或 `.claude/` 中包含文档相关 skill → 有则遵循项目 skill，本 skill 不生效
2. 项目根目录下是否已有 `docs/` 目录且包含 `_templates/` → 有则沿用项目已有的文档结构和模板
3. 以上都没有 → 使用本 skill 的规范，文档根目录为 `dev-docs/`

## 文档根目录

- 项目已有 `docs/` 目录 → 使用 `docs/`
- 项目没有 `docs/` 目录 → 使用 `dev-docs/`

以下用 `{DOC_ROOT}` 指代实际文档根目录。

## 作者字段

文档中的作者字段自动填写当前 git 用户名：

```bash
git config user.name
```

若获取失败则留空。

## 目录结构

```
{DOC_ROOT}/
├── README.md              ← 文档入口（文档索引）
├── _templates/            ← 文档模板（新建文档时复制使用）
├── assets/                ← 图片、截图、架构图等资源文件
├── conventions/           ← 开发规范、用户习惯、备忘录（持续更新，以最新为准）
├── features/              ← 功能文档（按功能聚合，日期编号排序）
│   ├── archive/           ← features 下已终态/失效 feature 归档
│   └── YYYY-MM-DD-功能名/
│       ├── 1-需求.md
│       ├── 2-设计-标题.md
│       ├── 3-实现.md
│       └── 参考/
├── adr/                   ← 架构决策记录（跨功能的技术决策）
│   └── archive/           ← adr 下已终态/失效 ADR 归档
├── wiki/                  ← 面向开发者的项目 Wiki（按主题分文件夹）
│   ├── architecture/
│   ├── development/
│   ├── features/
│   ├── operations/
│   ├── references/
│   └── archive/           ← wiki 终态/失效/移除内容归档
└── archive/               ← 其他跨分类归档（仅在没有对应分类 archive 时使用）
```

## 文档组织原则

**按功能聚合**：同一功能的需求、设计、实现规划、参考资料放在同一目录下，通过文件名前缀区分类型。

**务实落盘（强制）**：落盘文档只记录已确认的决策、已落地的实现、当前生效的约定、明确的执行步骤和可验证事实。默认不要把「推荐」「建议」「可以」「可选」「考虑」「后续可能」「不建议」「优先」这类不确定或候选表述写入正文。需要表达边界时，改写为确定性约束、当前范围、非目标、使用条件或已确认取舍。候选方案、风险提示、备选路线默认只在对话中说明；只有用户明确要求写入对比或备选方案时，才写入文档。

**日期编号排序**：功能目录以创建日期为前缀（`YYYY-MM-DD-`），文件系统中自然按时间排列。

**Feature 内文档按创建时间排序（强制）**：`features/YYYY-MM-DD-功能名/` 目录内的 Markdown 文档必须使用递增数字前缀命名，格式为 `1-`、`2-`、`3-`，按文档创建时间从早到晚排序。已有文档继续保留其原创建时间；新增文档取当前目录内最大编号加 1，不为插入排序而重命名旧文档。`参考/` 子目录内的参考文档使用独立编号段，从 `100-` 开始递增。

**README 索引排序（强制）**：`{DOC_ROOT}/README.md` 中的功能文档索引按创建日期降序排列，最新 feature 放在最上方；同一天多个 feature 按目录名自然排序。

**新功能新 Feature（强制）**：每次用户提出新的产品需求、业务功能、用户可见能力、具体功能方案、具体功能实现记录或功能参考沉淀时，不论内容是否与历史 feature 相似或相关，都必须在 `features/` 下创建新的日期编号 feature 目录。旧 feature 只能作为关联参考链接，不得默认追加、翻新或复用旧 feature 文档。全局技术选型、架构基线、基础设施选型、开发规范、工具链、部署运维、排障经验默认不创建 feature，应按文档路由表进入 ADR、wiki 或 conventions。

**实现完成即终态（强制）**：当某个 feature 对应实现已经完成并通过验收/验证后，必须同步将该 feature 下相关文档状态更新为终态：需求文档标记为「已完成」，技术方案标记为「已实现」，实现规划标记为「已完成」，并更新 `{DOC_ROOT}/README.md` 中对应 feature 状态。

**终态归档规则（强制）**：已经完毕、废弃或搁置的 feature 必须整体移入 `features/archive/`。ADR 标记为「已采纳」后继续保留在 `adr/` 活跃目录，只有「已废弃」或「已取代」的 ADR 才移入 `adr/archive/`。wiki 默认长期有效，只有确认失效、被替代、被拆分或从正文移除的内容才移入 `wiki/archive/` 对应主题目录。

**Wiki 面向开发者（强制）**：wiki 必须按主题分文件夹，内容尽量详细，面向参与开发的人，包含开发指南、架构说明、模块说明、常见坑、提示信息、备注、约定、排障经验等。与项目任何相关且会帮助后续开发的信息，都应沉淀到 wiki。

**翻新时清理失效内容（强制）**：翻新/更新文档时必须检查旧内容是否仍有效；确认失效的内容要从正文移除并归档到当前范围的 `archive/`；无法判断是否失效时必须询问用户，不能擅自删除或保留。

**独立于功能的文档**各有归属：
- 跨功能的架构决策 → `adr/`
- 通用知识沉淀 → `wiki/`
- 开发规范、用户习惯、备忘 → `conventions/`
- 已废弃文档 → `archive/`
- 全局技术选型、语言/框架/数据库/队列/部署选型 → `adr/`
- 本地工具链、开发环境、排障经验 → `wiki/development/` 或 `wiki/operations/`

## 文档命名规范

| 类型 | 文件名格式 | 示例 |
|------|-----------|------|
| 功能目录 | `YYYY-MM-DD-功能名/` | `2026-04-08-日志系统改造/` |
| Feature 内需求 | `N-需求.md` 或 `N-需求-子标题.md` | `1-需求.md` |
| Feature 内技术方案 | `N-设计-标题.md` | `2-设计-日志系统改造规划.md` |
| Feature 内实现规划 | `N-实现.md` 或 `N-实现-标题.md` | `3-实现.md` |
| Feature 内内容变更说明 | `N-内容变更说明.md` | `4-内容变更说明.md` |
| 参考资料 | `参考/` 子目录，文件从 `100-` 开始编号 | `参考/100-某调研.md` |
| ADR | `ADR-NNNN-简短描述.md` | `ADR-0001-不采用方案B.md` |
| Wiki | 自由命名 | `编码规范.md` |

Feature 内文件编号规则：

1. 编号从 `1-` 开始，按创建时间递增。
2. 同一时间创建多个 feature 根目录文档时，按需求、设计、实现、内容变更说明的顺序编号。
3. 在已有 feature 目录中新增文档时，先查看目录中已有 `N-*.md` 文件，使用最大编号加 1。
4. 不要为了让文档类型顺序更美观而重命名旧文档；编号代表创建时间顺序，不代表文档类型优先级。
5. `参考/` 子目录内资料必须使用 `100-标题.md`、`101-标题.md` 这类编号，参考文档编号从 `100-` 开始递增；新增参考文档使用当前 `参考/` 目录最大编号加 1。
6. Feature 根目录编号空间为 `1-` 到 `99-`；`100-` 起仅用于 `参考/` 子目录。
7. 不在 feature 根目录创建 `100-*.md`，不在 `参考/` 子目录创建 `1-*.md`。

## 文档元信息

每个文档头部必须包含：

```markdown
> 创建日期: YYYY-MM-DD HH:mm
> 作者: {git user.name}
> 状态: [状态值]
```

- 创建日期：文档首次创建时填写，之后不再修改
- 禁止自动添加或刷新「最后更新」「更新时间」等随修改变化的时间字段；已有字段在维护对应文档时移除，避免多人协作产生无意义的 Git 冲突。修改时间通过 Git 历史查询，只有用户明确要求时才写入文档。

各类文档的状态流转：

| 类型 | 可选状态 |
|------|----------|
| 需求 | 草稿 → 评审中 → 已确认 → 已完成 → 已废弃 |
| 技术方案 | 草稿 → 评审中 → 已采纳 → 已实现 → 已废弃 |
| 实现规划 | 规划中 → 进行中 → 已完成 → 已搁置 |
| ADR | 提议 → 已采纳 → 已废弃 → 已取代 |
| 参考文档 | 无状态流转 |

## 工作流程

### 1. 初始化文档目录（首次使用）

如果 `{DOC_ROOT}` 不存在，创建完整目录结构：

```
mkdir -p {DOC_ROOT}/{_templates,assets,conventions,features,adr,wiki,archive}
```

然后：
1. 按 @references/templates.md 创建 `_templates/` 下的所有模板文件
2. 创建 `README.md` 文档索引（模板见 @references/templates.md 末尾）
3. 检查 git 跟踪状态，决定是否将 `{DOC_ROOT}/` 写入 `.git/info/exclude`（见 @references/rules.md「Git 提交规则」）

### 2. 新建功能文档

1. **查重但不复用**（强制）：先按 @references/rules.md「创建前查重」检查是否已有相似文档；相似文档只作为参考链接或归档判断依据，不得阻止创建新 feature
2. 在 `{DOC_ROOT}/features/` 下创建 `YYYY-MM-DD-功能名/` 目录
3. 根据需要创建对应文档（需求、设计、实现），使用 @references/templates.md 中的模板，并按创建时间使用 `1-`、`2-`、`3-` 前缀命名
4. 更新 `{DOC_ROOT}/README.md` 的文档索引，功能文档索引按创建日期降序排列

### 3. 新建 ADR

1. 查看 `{DOC_ROOT}/adr/` 下已有编号，取下一个编号
2. 创建 `ADR-NNNN-简短描述.md`，使用 @references/templates.md 中的 ADR 模板
3. 更新 `{DOC_ROOT}/README.md` 的 ADR 索引

### 4. 更新文档状态

文档状态变更时，更新文档头部的状态值，同步更新 `README.md` 索引中的状态列。

实现完毕后必须执行 feature 完成标记：将该 feature 下需求/设计/实现规划等相关文档更新为对应终态，并在 `README.md` 功能索引中标记 feature 为「已完成」或更精确的终态说明。

文档进入归档条件后必须执行归档：已完毕、已废弃或已搁置 feature 整体移动到 `features/archive/`；已废弃或已取代 ADR 移动到 `adr/archive/`，已采纳 ADR 保留在 `adr/`；失效、被替代、被拆分或从 wiki 移除的 wiki 文档/段落移动到 `wiki/archive/` 对应主题目录；同步更新 README/wiki 索引。

### 5. 归档文档

按 @references/rules.md「归档规则」操作。

## 引用文件

详细的模板、规则、Wiki 维护要求拆分在以下文件中：

- @references/templates.md -- 所有文档模板（需求、设计、实现、ADR、参考、Changelog、Wiki、README 索引）
- @references/rules.md -- 归档规则、图片资源规范、创建前查重、修订记录、Git 提交规则
- @references/wiki-rules.md -- Wiki 维护规则（强制）、内容要求、推荐文档清单
- @references/conventions.md -- conventions/ 目录规范、记录内容、更新规则

## 注意事项

- 文档中不使用 emoji，使用纯文本符号替代（如 `[v]` `[x]` `[!]` `[?]` `-->` `<--` 等）
- 编写文档时使用项目对应的语言（中文项目用中文，英文项目用英文）
- 代码示例使用项目实际的技术栈语言，不预设任何特定语言或框架
- 验证计划中的命令应匹配项目实际的工具链
- 文档间通过相对路径互相链接
- 每次新增/修改文档后，同步更新 `README.md` 索引
- README 功能文档索引按创建日期降序排列，最新 feature 放在最上方
- 当用户要求“按文件解释做了什么”“总结本分支改动”“内容变更说明”等代码改动说明时，必须在同一 feature 目录下新建或更新 `N-内容变更说明.md`；不要把按文件变更说明写入 `N-实现.md`。实现规划只保留指向 `N-内容变更说明.md` 的关联链接。
- feature 内文档必须使用 `1-`、`2-`、`3-` 这类数字前缀，并按创建时间递增；新增文档使用当前目录最大编号加 1，不重命名旧文档。
- `参考/` 子目录内参考文档必须从 `100-` 开始编号，且不占用 feature 根目录 `1-99` 编号空间。
- 新产品需求、新业务功能、新用户可见能力、具体功能方案、具体功能计划、具体功能实现记录默认创建新 feature；即使与旧文档相关，也只链接旧文档，不把新内容写入旧 feature 文档
- 全局技术选型、架构基线、基础设施选型、开发规范、工具链、部署运维、排障经验默认不创建 feature，应按文档路由表写入 ADR、wiki 或 conventions
- feature 实现完成后，必须把 feature 及其相关文档标记为已完成/已实现等终态
- 已完成、已废弃或已搁置的 feature 必须移动到 `features/archive/`；已采纳 ADR 保留在 `adr/`，只有已废弃或已取代 ADR 移动到 `adr/archive/`；wiki 默认长期保留，只有失效、被替代、被拆分或移除内容才归档
- wiki 必须按主题分文件夹，内容面向开发者并尽可能详细；项目相关提示、备注、开发经验都应写入 wiki
- 代码改动后仅在 API 行为、配置、部署、任务调度、数据模型、公共能力、脚本入口、开发约定或排障经验发生变化时更新 docs/wiki；纯重构、格式化、测试补充、内部实现微调默认不更新 wiki
- 翻新文档时必须移除已失效内容；不能确定是否失效时先询问用户；移除内容必须归档
- wiki 中所有引用必须指向真实存在的路径/符号，禁止凭记忆编造路径
- 每次修改文档内容后，追加修订记录（详见 @references/rules.md「修订记录」）
- 各类记录文档及历史记录区默认仅在末尾追加；未经用户明确要求，不改写、删除、合并或重排旧记录。新增记录简洁干净，仅保留必要事实、关键结论与验证边界；错误通过追加更正说明处理。
- 文档中标注为「可选」或「推荐」的内容（如可选的实现步骤、备选方案建议等），仅口头输出给用户，不写入文档。只有用户明确要求写入时才将其纳入文档
- 对于需求文档、技术方案文档、实现规划文档：如果存在多个可行方案，默认只在对话中口头向用户说明并协助选择；**不要把多个候选方案、方案对比、备选方案列表写入文档**。文档中只保留用户已确认的最终方案。只有用户明确要求“把备选方案/方案对比写入文档”时，才允许写入。
- 写入文档前先做一次务实性检查：正文中若出现「推荐」「建议」「可以」「可选」「考虑」「后续可能」「不建议」「优先」「暂时」「应该」等词，逐条判断是否属于不确定/候选表述；属于则删除、改成确定性约束，或移到对话回复中说明。排障条件句、历史修订记录、状态占位（如「暂无」）可以保留。
- 文档长度按问题复杂度控制：简单决策/调研 300-800 字，普通技术方案 800-2000 字，跨模块改造可超过 2000 字；不要为了套模板补空章节，没有内容的章节应删除或合并。
